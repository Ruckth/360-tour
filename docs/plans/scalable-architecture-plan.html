Scalable Architecture Plan

The goal is a codebase that is faster and safer to build on, with an architecture simple enough to state in five rules. The work is about five weeks. First we close two security holes. Then we delete dead code and reset the schema to its final names. Then we rebuild messaging, the most duplicated area, and draw domain boundaries one PR at a time, with no feature freeze. Anything that is really a new product feature waits until a feature needs it.

Target architecture: five rules

These rules go into ARCHITECTURE.md. Rules 2–5 are enforced by lint in Phase 3.

  1. One deployment serves one resort.

    We sell a custom build to each client (BUSINESS_PLAN.md), so delete tenants and tenantId. Anything an admin can edit lives in Convex. Build-time brand and theme live in src/config.

  2. Each domain owns its tables and functions, and exposes one file.

    Backend code lives in convex/<domain>/. Other domains may import only convex/<domain>/model.ts, which holds plain helpers that take the caller's ctx, so cross-domain work stays inside one transaction. Every other file in the domain is private to it.

  3. Each business rule is written once, in convex/shared/.

    Money, dates, resort time, pricing, overlap and time-off rules are pure code. shared never imports _generated/server or takes a ctx. src imports only convex/shared and convex/_generated, and convex never imports src.

  4. Every public function states who may call it.

    Only convex/auth/ may import the raw query, mutation and action builders. Everything else uses publicQuery, guestQuery/guestMutation (needs the chat session token), deviceQuery/deviceMutation (needs the display token), adminQuery/adminMutation/adminAction, or internal*. Once feat/staff-roles lands, add staffQuery/staffMutation on top of its role model.

  5. Types run end to end, and money is integer satang.

    No as never. Functions that need no login return explicitly listed fields and declare return validators. New code throws ConvexError({ code, message }) for failures the user should see.

Decisions for you

Each has a recommended default, and the plan goes ahead with it unless you say otherwise. changed marks a recommendation that changed after review.

D1

Tenancy

Recommended One deployment per resort. Delete tenants and tenantId (10 references in 5 files).

Alternative: build organizations and memberships now. That would touch every table and every access check, for a SaaS model the business plan mentions only as a Year 3 idea.

D2

Demo mode without Convex

Recommended Drop dev:demo, useOptionalConvex and the demo branches. CI and local development run against a seeded local Convex backend.

This is a medium-sized task on its own. 9 of the 10 E2E specs depend on demo mode (for example bookingId=demo at tests/e2e/booking.spec.ts:42), so the change, a local backend in CI, a seed step, a Clerk test user and the rewritten specs must land in one PR. Keep the checkout preview fixture as a design tool, but stop it from re-implementing the money rules.

D3

Payments model changed

Recommended Keep the current payment tables. Switch all money to integer satang with one rounding function, behind tests that pin down today's behavior. Postpone a unified ledger.

v1 said a POS settlement recorded the same money three times. It doesn't: the stay payment is a link to the order (method: 'order', convex/bookings.ts:240). The real bug is rounding. Stay pricing turns a 10% discount on 100.50 into 10 (convex/lib/pricing.ts:19), while POS gives 10.05 (convex/lib/orderMath.ts). Revisit the ledger when split payments across a stay and spa become a real need.

D4

Where webhooks run moved earlier

Recommended Move them to Convex httpActions, and do it in Phase 2, before the general file move.

This is the biggest win in the plan. It removes 37 of the 61 casts, all 20 secret-protected mutations, and the Next.js route that calls the AI inside the request with a 22-second timeout per event (src/lib/chat/messaging-reply.ts:128). Doing it first also means those files aren't moved in Phase 3 and then deleted.

D5

Source of villa content

Recommended Convex is the only runtime source for content admins edit: properties, reviews, pricing and social proof. resort-config.ts stays in code; the unused booking-config.ts is removed.

28 files import @/lib/data today, and the server and client read different endpoints.

D6

Renames changed

Recommended Do these during the Phase 1 reset: bill*→order*, serviceAppointments→appointments, rooms→tourScenes, chatSessions→conversations, chatMessages→messages, socialProof→reviewStats. Keep customers.

The code already says "order" (orderLinks, orderLifecycle), and a room here is really a 360° tour scene. Renaming in Phase 1 means later moves carry the final names, so no line is touched twice.

How it runs without you

The loop below repeats until the Phase 4 gate passes. Each step either finishes or stops at one of the listed stop points, so nothing waits on you by accident.

  1. Pick the next step. Claude reads pnpm arch:score --json and takes the first failing metric in the lowest unfinished phase.
  2. Delegate. Codex (backend, data, money) or Kiro (UI, copy, docs) works in its own worktree branched from the current origin/main. Its brief contains the plan item, the metric ids it must move, the exact test titles, and the out-of-scope list.
  3. Self-check. The implementer runs the scorecard and the standard commands, then hands back with its branch, its head SHA, and the before and after metric values.
  4. Gate. Claude reruns both checks on the branch, reviews the diff, and confirms that no metric due in an earlier phase got worse. Every change to money, access, webhooks or the reset also gets an independent audit by a second model.
  5. Fix or stop. If the gate fails, the implementer gets the findings and tries again, at most twice. A third failure stops the step and reports what was tried.
  6. Ship. The branch becomes a PR with the scorecard diff in its description. It merges according to the merge rule below, and then the loop picks the next step.
  7. Ratchet. When a phase gate passes on main, its number is written to .arch-phase. CI runs pnpm arch:score --phase $(cat .arch-phase), so a finished phase can never quietly regress. Adding this CI step is part of Phase 0.

Merge rule. The current rule: Claude opens each PR once it passes its gate, then waits for your approval to merge. PRs are batched so you approve once per phase. Alternative, available if you switch to it: PRs that pass their gate merge automatically, except money, access, webhook and reset changes, which still wait for you.

It stops and asks you only for

  • Running the reset runbook on production
  • Turning provider webhooks or Stripe off or on, and setting secrets in provider consoles
  • A failed gate after 2 retries
  • A step that would change a decision (D1–D6) or touch something in "Later"
  • Any metric due in an earlier phase getting worse on main

Status you can check anytime

  • pnpm arch:score shows every metric with ✓/✗ and how far each phase has got
  • Each PR description shows the scorecard before and after
  • One summary at each phase gate: metrics moved, PRs merged, anything parked

What changed after review

Codex (gpt-6.1-sol) checked every claim against the code as of 12 Nov. Kiro (Opus 5.5) reviewed the plan for scope and simplicity. Claude confirmed each point that overturned v1 before accepting it.

  • Smaller scope, about 5 weeks instead of 8. The payments ledger, contact identities, staff roles, outbox, audit merge, route groups and src/features moved to "Later" (Kiro).
  • D3 reversed. Settlement links the stay payment to the order instead of recording it twice. The real fix is satang and one rounding function (Kiro, confirmed at bookings.ts:240).
  • New order: start from a clean tree, then put the renames and satang in the Phase 1 reset, then messaging before the general move, so no code is moved twice (Kiro).
  • Guest token moved into Phase 0, with a spec. respond and 11 chat functions trust any session ID (Codex, Kiro).
  • Reset runbook added: clear data while the old code is still deployed, because Convex validates stored documents against the new schema. Seed scenarios replace a seed that exits early (Codex).
  • Money cutover safety: remove the Stripe × 100 step and acknowledge old Stripe events instead of answering with a 500 (Codex).
