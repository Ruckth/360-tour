# Appointment finance and Stripe implementation handoff

This worker implements only the assigned appointment finance, Stripe, expiry and dedicated helper/test scope. No commits, push, deployment, installation, live data writes, actual refund API requests, browser work or subagents. Parent-owned POS, orderLinks, bill/billLines schema, booking UI/customer/checkout files were not edited. Concurrent appointment/configuration/schema changes are retained. Parent mounts `AppointmentFeeAction` after this handoff; no no-show fee implementation was duplicated here.

## Delivered appointment behavior

`convex/lib/appointmentFinance.ts` is the transaction helper; public APIs remain in `adminServices.ts`. `getAppointmentFinancials({appointmentId})` requires admin and returns `{revision,money:{gross,refunded,net,owed},payments,refunds,orders,unitemised}`. Every collection reads 201 and refuses above 200 rather than silently approving against a truncated financial prefix. Legacy paid/refunded documents derive known amounts from the existing price/status only; no original payment actor, tender, payment time or payment row is invented. Actual POS prices already use the settled line net, including discounts.

- `markAppointmentPaid({appointmentId,expectedRevision?,effectiveAt?,method?,idempotencyKey?})` now writes an `appointmentPayments` row and appointment history atomically. New sheet supplies a stable key, revision, method and actual business date. Optional old arguments retain compatibility (`unrecorded` method). An explicit-key replay checks the stored method/time before returning the original payment. Only unpaid, noncancelled, unrefunded appointments can be marked paid. Existing/open receipt guards remain, and receipt-owned money cannot be relabelled manual.
- `refundAppointment({appointmentId,expectedRevision?,effectiveAt?,amount?,currency?,method?,reason?,idempotencyKey?,paymentId?,billId?})` supports partial/full independent refunds. Amount-based calls require revision, currency, method, reason and key. Choose at most one source, capped at both that source's actual remaining money and the appointment's actual net money. POS source is the actual charged billLine/receipt, with an original receipt link. A source is required when itemised money or a paid receipt exists. Unitemised legacy payments can refund their known remaining amount without an invented payment row.
- Refund rows contain actor, server recorded time, business effective time, reason, method, currency, source and before/after net. Explicit-key retry returns the same row before stale-revision checks and rejects changed amount/currency/method/reason/source/time. Partial refund keeps `paymentStatus:paid`, full refund uses `refunded`; both preserve the actual appointment lifecycle, original price and receipts. Owed remains zero after either; refunded money does not become collectible again.
- The legacy no-amount full-refund call writes a new `unrecorded` method row with an explicit legacy explanation at actual recording time. Duplicate legacy calls retain the existing safely refused behavior. An already-refunded legacy flag reads fully refunded and does not create reconstructed historical rows.
- `correctAppointmentPaymentEntry({appointmentId,expectedRevision,paymentId,idempotencyKey,action:'amend'|'cancel',reason,method?,effectiveAt?})` is admin-only and manual-only. Amendment preserves original recorded time/actor, records old/new tender/date, and keeps amendment actor/time. Cancel is only a mistaken unreceived manual entry, never a refund; refunded money and receipt-owned money are blocked. It preserves actual lifecycle. A dedicated correction attempt table makes a lost-response retry idempotent even with its original now-stale revision.
- Appointment finance changes use `recordAppointmentChange` for both existing appointment history and generic record history in the same transaction. Finance fields/entry IDs/method diffs are selected explicitly; no access tokens or credentials are included. The internal financial revision ensures an amendment with the same summary values is still auditable; the UI hides that internal counter.

`AppointmentFinancials.tsx` is mounted in AppointmentSheet. It exposes amount/method/date/reason forms, source receipt links, manual amendments and “Not received…”, accurate net/refunded/to-collect totals, readable payment/refund provenance and legacy unknowns. Existing direct full-refund/paid buttons are replaced by these forms. All use incumbent `ChangeConfirmDialog`; pending disables fields/duplicates/dismissal, errors retain the draft, and retry freezes the submitted values/key/revision. Existing status and scheduling dialogs remain.

Schema scope: optional appointment `amountPaid`, `amountRefunded`, `financialRevision`; new `appointmentPayments`, `appointmentRefunds`, `appointmentPaymentCorrections`. New functions are in an already generated module; generated API files were not hand-edited.

## Delivered Stripe and expiry behavior

`http.ts` still verifies the exact raw request signature first. `charge.refunded` now forwards the real event ID/created time, charge ID, PaymentIntent ID, currency, charge amount, cumulative amount refunded, and any included refund IDs/amounts/currencies/statuses. This necessary HTTP adapter edit is included in this worker's files.

`payments.recordRefund` accepts internal `{paymentIntentId,chargeId,eventId,eventCreated,amount,amountRefunded,currency,refunds}`; monetary provider inputs are integer minor units. It validates finite/safe/nonnegative/range/currency/source-money invariants. It resolves modern provider payments by their indexed PaymentIntent, retaining correctness when a booking later has another payment, with a conservative legacy fallback only for a provable unitemised Stripe payment. A missing payment/booking fails for provider retry; it does not acknowledge a refund before payment reconciliation.

`stripeRefundCharges` is an authoritative per-charge high-water mark. A newer cumulative snapshot writes only its positive delta in `bookingRefunds`, with charge/event identifiers and cumulative amount, advances the checkpoint and booking revision/history atomically, and updates source payment refunded money. Duplicate events, distinct events with the same cumulative total and older/out-of-order snapshots write nothing. Cumulative amounts, not event timestamp ordering, drive accounting. Ledger effective time is the provider event's creation time, explicitly distinct from server recording time. No provider refund API is called. Refunds preserve stay occupancy/lifecycle; zero net becomes payment-refunded, not automatically cancelled.

A legacy already-fully-refunded flag already nets to zero. Incoming provider evidence can supply a real provider refund ledger row, labelled as already covered by that legacy balance, without inventing an original payment row or subtracting again.

Manual Stripe reconciliation deliberately requires evidence:

1. Existing unlinked manual `bookingRefunds(method:'stripe')` blocks provider reconciliation instead of guessing by matching amount. HTTP returns 500 for retry.
2. `api.payments.linkRecordedStripeRefund({bookingId,refundId,expectedRevision,chargeId,providerRefundId})` requires admin and actual `ch_...`/`re_...` identifiers. It links once, checks global duplicate refund IDs, rejects receipt/manual-money source contradictions and logs actor/revision atomically. It is available for parent booking-finance UI integration; this worker does not own that component.
3. Replay a charge snapshot that actually includes the linked refund ID with matching minor-unit amount/currency and successful status when supplied. Its linked manual amount is already counted, so only the additional cumulative delta is added. Source payment attribution is reconciled too. A truncated snapshot missing the explicit evidence fails, never guesses.
4. Once a charge has been reconciled on a booking, `recordStayRefund(method:'stripe')` refuses later hand-entered duplicates and directs staff to replay provider events. Other refund methods retain the existing desk path.

Checkout generation reserves the actual remaining unwaived balance, not the whole original stay total. A prior deposit is preserved, while the new `bookingPayments` row records exactly the provider amount received. `stripeCheckoutAmount` freezes the session amount; save and completion recheck attempt, balance, currency, dates, current session and safe integer minor units. Wrong/stale/superseded sessions and mismatched amounts fail before money/history changes. Explicit completed-session replay checks amount/PaymentIntent and writes nothing. Completion clears its live URL/expiry protection so completed checkouts do not unnecessarily block desk corrections. A mismatched live legacy full-total session is refused until expiry; it is never reused to overcharge a deposit.

Unrecoverable stale provider completion is a reconciliation refusal (HTTP 500), not a claim that payment did not happen. Parent must surface provider delivery failures operationally; this slice does not expose a new provider incident console or call Stripe to expire/refund sessions. A completion arriving before session save can retry after save. A permanently superseded paid session requires explicit support reconciliation rather than automatically occupying a conflicting stay.

`payments.expireCheckout` now records atomic booking history/revision, cancellation actor/time where applicable, and preserves a confirmed/admin-created stay. `crons.expirePending` similarly records system actor/time and revision/history. Checkout secrets/URLs/request tokens are excluded from history.

## Primary provider evidence read

- [Stripe event types](https://docs.stripe.com/api/events/types): `charge.refunded` is emitted for partial and full refunds and its data object is a charge.
- [Charge object](https://docs.stripe.com/api/charges/object): charge ID, amount, amount_refunded, currency and payment_intent are charge fields. They are not a standalone refund object.
- [Refund object](https://docs.stripe.com/api/refunds/object): individual refund IDs, amount in smallest currency unit, created time, payment_intent and status are separate refund evidence.
- [Webhook delivery and duplicate handling](https://docs.stripe.com/webhooks): deliveries are retried, ordering is not guaranteed, event created timestamps are not an ordering/dedup key, and raw-body signature verification is required. This implementation uses per-charge monotonic cumulative amounts with event evidence, never arrival time or amount-only manual matching.
