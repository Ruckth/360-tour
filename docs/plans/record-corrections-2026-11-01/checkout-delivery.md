## Delivered user flows

- **Payment review:** PayPanel captures due, order revision, linked customer ID and its reviewed revision when payment opens. A reactive order/customer/source change invalidates an unsent review. It never fetches/substitutes a new customer revision while sending. The first submitted attempt also freezes tenders, actual received time, notification choice and key. Controls lock while pending. A failed/lost response offers Retry payment with the identical args, or explicit renewed order review. Successful replay remains possible after customer edits/merge, because the backend replay branch runs first. Unmounted payment completion does not navigate back to an earlier order.
- **Actual received date:** explicit date/time input in Bangkok time, with no past-day cutoff in the UI. The received timestamp is separate from `paidAt`, which remains receipt issue time. An optional stay payment confirmation checkbox is explicit and initially off. The fixture sends no emails. Backend effective-date validation remains authoritative (currently dates from 2000 onward and up to five minutes clock skew); UI asks for a valid time no later than now.
- **Payment corrections:** receipt controls expose tender, actual received date and payer recording corrections. Split tender correction supports adding/removing rows within the backend's three-tender limit; its total is validated against original money received. Customer selection captures the visible profile revision; no automatic match. Each correction freezes the viewed correction revision and its complete first submitted payload, retains fields/errors after failure, and retries with the same key/args. Untouched received dates retain their exact original seconds/milliseconds. Closing and reopening explicitly starts fresh review.
- **Mistaken entry:** a separate Payment entered by mistake action requires both a reason and an explicit checkbox asserting that no money was received. It calls `voidUnreceivedOrder`, displays real backend refusal reasons, and does not claim to send a refund or reverse provider money. Ordinary Void remains available with clarified copy: money/source state remains, and it does not record/send a refund. Its dialog blocks duplicate submits and dismissal while pending.
- **Original receipt:** `.pos-receipt`, original `payments`, `receiptCustomer`, receipt number and share/copy output retain their issued snapshots. Current operational tenders/customer/received time are rendered separately outside the printed article. Amendment before/after, reason, actor and recorded date appear alongside it. Linked stay refunds show recorded amount/method/reason, effective and recorded dates, actor and stay reference, explicitly as records of money returned elsewhere.
- **History:** OrderPanel and ReceiptView expose the actual paginated `orderHistory` reader. Loading, empty, first-page/continuation errors with retry, loading-more, and full cursor continuation are supported. Rows show actor, recorded/effective dates in Bangkok, selected labelled business fields, before/after and explicit cleared optional fields. Clear snapshots enumerate removed contents. No raw JSON dump. Customer history now also labels recorded/effective dates and cleared contact fields. Existing receipt activity is separately readable and explicitly labelled as the bounded latest activity.
- **Customer merge:** submission is active in production and fixture. Explicit identity review/reason is required; same names are never merged automatically. Source/destination revisions and first-submitted merge inputs/key remain stable on retry. The source retains its ID, profile/history and archive/merge destination. Paid receipt/customer/tender snapshots remain untouched. Profile progress distinguishes running from completed and counts moved references. Resume merge is available for interrupted jobs. Pending resume cannot navigate into the kept profile mid-write.

## Actual API contracts used

Types come from the real existing Convex modules (`FunctionArgs` / `FunctionReturnType`), without casts to invented return shapes or generated-file patches.

- `pos.settleOrder({orderId,idempotencyKey,expectedDue,expectedRevision,tenders,effectiveAt?,notifyGuest?,expectedCustomerRevision?})`. Linked customer revisions are now required in practice because `CUSTOMER_POS_INTEGRATION_ENABLED` is true. Missing/stale customer revisions and merged identities reject after successful replay handling; existing linked archived identities can still pay after review. `pos.linkCustomer` already calls `assertCustomerCanLink` before same-customer early return/new order mutation, rejecting archived/merged new links. Verified against actual implementation and backend tests; this worker did not modify pos.ts.
- `pos.amendOrderPayment({orderId,expectedCorrectionRevision,idempotencyKey,reason,tenders?,effectiveAt?,customer?:{customerId:Id|null,expectedCustomerRevision?}})` returns `{sequence,replayed}`. Reason maximum 500. Paid orders only; original payment amount is preserved. Payer omission keeps current recording, null removes named payer, selection sends its reviewed revision. Current backend checks same-key replay before revision; frontend keeps the full original payload stable regardless.
- `pos.voidUnreceivedOrder({orderId,expectedCorrectionRevision,idempotencyKey,reason})` returns `{replayed}`. The no-money assertion is an explicit frontend requirement, not an invented API argument. Current backend proves each linked reversal, retains deposits/receipt evidence and refuses ambiguous legacy/refunded/changed sources. This worker did not alter those semantics.
- `pos.getOrder({orderId})`: consumes actual `paymentRecord.{effectiveAt,tenders,tendersAmended,customer,customerAmended,correctionRevision,voidUnreceived}`, `corrections`, `refunds`, original `payments`, `receiptCustomer`, `audit`, source references and totals. The backend currently returns newest **20 corrections**, at most **50 billAudit** entries and a bounded stay-refund collection. UI reports older amendments are retained when `correctionRevision` exceeds returned rows; it does not claim these bounded arrays are paginated/all-time readers.
- `pos.orderHistory({orderId,paginationOpts:{numItems,cursor}})` returns native Convex `{page,isDone,continueCursor,...}` of `recordChanges`, entity type `order`, newest first, page size 1–50. Adapter requests 20 and uses `usePaginatedQuery`. Ordinary item changes/cleared snapshots live here; historical `billAudit` and financial amendments are separate streams.
- Existing customer browse/edit/archive/history/order APIs remain. `getCustomer` additionally returns `mergeProgress: customerMergeJobs document | null`, plus `mergeEnabled:true`.
- `customers.mergeCustomers({sourceId,destinationId,sourceRevision,destinationRevision,reason,idempotencyKey})` retains `{replayed,destinationId}`. A successful response means the durable merge was started; completion is `mergeProgress.status === 'completed'`, never inferred solely from that response.
- `customers.resumeCustomerMerge({sourceId})` authenticates with `requireAdmin`, advances one bounded batch and returns null. `customers.continueMerge({jobId})` is an **internalMutation** invoked by the scheduler via `internal.customers.continueMerge`. It accepts no actor/auth argument; history uses the initiating admin stored by the authenticated start transaction. All new public reads/writes remain on the app's existing single admin role.

## Durable merge design and concurrency

New `customerMergeJobs` table only: source/destination, derived actor, reason, running/completed status, moved count, selected typed pre-merge identities, created/updated/completed timestamps. Indexed by source and destination/status. No arrays of order IDs, unbounded counters-by-scan or financial schema modifications.

Start validates both reviewed revisions, marks source merged/archived and increments both identity revisions **before** moving references, then writes the durable job/start history and processes up to 100 rows in the same transaction. Each continuation reads at most 101 remaining source references and moves 100, appending their order history and updating job progress transactionally. The indexed set of bills still pointing at the frozen source is the durable work queue: consuming its head avoids a cursor over an index being changed by the migration. No new links can enter that set. Ordinary bill IDs/numbers, updatedAt ordering, lines, payments, source links and issued snapshots stay intact. Draft/held order revisions increment exactly once when moved.

A chunk that fails rolls back its references/history/progress/scheduling together. Start replay never adds another job/start/completion event. Duplicate scheduler deliveries/manual resumes serialize through the job document and shrinking reference set; moved rows cannot be processed again. Only the transaction exhausting the source writes completed and the two completion history rows. A stopped scheduled job remains visibly running and can be resumed without a misleading partial completion.

Concurrent independent merges **into the same destination are supported**, with its real reviewed revision/OCC protection. A destination cannot itself be merged away while any incoming job is running, preventing an unfinished chain. Customer edits/archive changes remain revision protected and do not scan or patch order populations. The temporary >100-nonempty/>1000-linked edit fallback was removed entirely. Settlement's read/check of the customer participates in the same Convex transaction as payment, so corrections/merge starts conflict atomically with payment. Unmoved source links reject as merged; moved links require refreshed order and kept-customer review.

## Fixture behavior

The fixture implements payment records, actual received dates, correction revisions, financial before/after entries, original immutable receipt snapshots, amendment/void replay, exact-total tender validation, customer revision/archived/merged guards, bounded merge jobs/continuation/progress/resume and real paginated new order/customer history. Adds/removes/quantity/staff/time/discount edits and cleared contents produce snapshots matching production's selected line fields. Customer merge start/completion and per-order events retain reasons.

Fixture settlement retains proven per-source payment data. Mistaken-entry reversal only reopens the order's proved linked payments, restores an appointment's pre-checkout price and preserves a stay's online deposit. Imported `recordedRefunds` can be supplied to `createFixtureBackend({recordedRefunds:[{billId,...actualRefundFields}]})`; they are filtered by exact billId, displayed faithfully and prevent an unreceived-money reversal. This is a fixture seeding seam for booking-origin ledger entries, **not a fixture-only checkout refund action**. Normal fixture orders begin with no refunds/corrections because none have been recorded; actual correction actions populate the collections. No fake discard/restore, no-show fee or appointment partial-refund actions were added.
