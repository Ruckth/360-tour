# Stock and Dashboard rollout

## Roll forward

1. Record the deployed application and Convex revisions. Take a restorable backup and record control totals for purchase orders, receipts, stock movements, on-hand quantities and open incoming quantities. Include samples of order revisions, receipt lines, linked ledger entries and variant IDs.
2. Deploy the widened Convex schema, indexes and functions. Wait for schema validation and index readiness. Verify that an existing receipt can be reopened and an old-client receipt request can be retried with its original operation key.
3. Run internal `commerce/purchasing:backfillPurchasingLegacy` with `{"table":"purchaseOrderLines","cursor":null}` and pass each `continueCursor` back until `isDone`. It values each pre-feature PO line exactly from its receipt lines (accepted − corrected at each receipt's recorded cost, plus rejected units). It never estimates. Each line with more than 100 receipts is returned in `pending`. Run internal `commerce/purchasing:rebuildPurchaseLineValuation` for each pending line with `{"orderLineId":…,"cursor":null,"acceptedValue":0,"rejected":0}`, then pass the returned totals and cursor back until `isDone`. Until that point, receiving, corrections and repricing on that line fail with the retryable `VALUATION_PENDING`. Then run the same backfill for `purchaseOrders` (reference codes, plus value summaries once every line is valued), `purchaseRequests` (reference codes for fragment search) and `supplierReceipts` (the exceptions-view flag). Orders with an unvalued line keep their previous total and show received value as pending. Check sampled orders' received value against their receipt lines, legacy reference lookup and receipt exception flags.
4. Run the internal `commerce/purchasing:backfillSupplierData` mutation for each source, `orders`, `receipts` and `contacts`. Start with `{"source":"orders","dryRun":true}` to preview a batch. Repeat each source with `dryRun` omitted until a follow-up call reports both `isDone: true` and zero processed. Check legacy suppliers' open-order counts, delivery history and contact matching before relying on the projections.
5. Run internal `commerce/stock:backfillVariantSearch` with `{"paginationOpts":{"cursor":null,"numItems":25},"continueBatches":true}`. Verify older variants in catalog search after scheduled batches finish. Historical activity already uses the legacy row data. The optional `commerce/stock:backfillMovementFilters` refreshes actor search keys only. Pass 25 items and each returned cursor until `isDone`. Check that historical reason codes still match the retained evidence.
6. Release the application and verify receiving, stock activity, legacy variant search and the finance dashboard using the appropriate roles. Reconcile receipt quantities against stock movements and open incoming quantities for the sampled orders.

## Roll back the application

Keep the widened Convex schema, indexes and compatible function deployment. Restore the previous application and smoke-test legacy requests against that backend. Check receipt and order detail, replay a receipt with the same operation key, and verify that the replay creates zero additional receipts or movements. Compare stock and purchasing control totals with the pre-rollback readings and account for any writes during the interval. Check which active orders or custody states require controls introduced in the new application. Route those cases to a compatible admin workflow before restoring old-client traffic.

A rejection requires a coded reason and a supplier return requires a recorded outcome. An older open tab receives `CLIENT_UPDATE_REQUIRED` before either command posts. During normal rollout, reload the updated application and re-enter the reason or outcome. During a frontend rollback, keep a compatible receiving client available for these two workflows. Set the over-delivery tolerance to zero before returning traffic to clients that calculate remaining quantities using the older formula.

If prepared profitability views must be drained, follow [Profitability snapshot rollback](profitability-snapshot-rollback.md) through the repeat drain check. Keep the pause active while rolling back application traffic if prepared pages need to stay unavailable. The finance guide’s previous-backend step applies only after the Stock and Purchasing downgrade prerequisites below have also been met.

## Prerequisites for a strict backend downgrade

Quiesce writers and scheduled work that can create widened records. Restore a copy of the current data in isolation and inventory validator differences, pending jobs and index dependencies against the exact rollback revision. Include nested fields and new enum values, both source and derived tables, and data persisted by backfills. Prepare an audit-preserving conversion for every incompatible record and agree on how the older application will handle any state it cannot represent. Validate the old schema on the converted copy and reconcile IDs, quantities, money, and audit history before choosing a downgrade window. Retain a restorable copy of the widened state.

## Local rehearsal

An isolated Convex instance started on `ef637a55` and accepted a purchase order, a partial receipt, and a profitability source view. After deploying the widened backend, the stored records matched the baseline. Supplier backfills processed one order, one receipt and ten contacts, then returned zero on repeat calls. The activity backfill restored the missing actor key without changing the mixed-case reason code. The variant backfill restored search metadata and a normalized SKU lookup found the original product. The line-first operator backfill reconstructed 15,000 satang of accepted value from the legacy receipt and matched the order summary. It also populated legacy request reference metadata and receipt exception flags. Each backfill returned zero updates on repeat. The fixture did not exercise the separate rebuild for lines with more than 100 receipts.

After old-client receiving, new-client receiving with a 20,000 satang invoice total, and an old-client receipt against the retained backend, the fixture held two orders, four receipts, four ledger movements, ten units on hand and ten units incoming. Replaying the original and rollback receipts added no rows. Three units stayed assigned to a bin while the legacy receipt increased unassigned stock from six to seven. The reorder point remained at 12 units with revision 1. The profitability drain removed an actual prepared view and a synthetic 35-chunk child, plus synthetic building and failed sources, while retaining the original source. With the drain complete, Convex still rejected the strict `ef637a55` downgrade because the supplier validator lacked `contactKeysApplied`.

The rehearsal used legacy API payloads for the application rollback path. It did not deploy a previous frontend build or measure migration throughput on production-sized data.

### Mature profitability fixture

On disposable Convex, the four-lane worker processed 10,000 in-period appointments linked to orders, 4,001 earlier appointments and 6,002 customers. The timestamp endpoint returned HTTP 200, and the SDK's pinned query did not see a write committed after it captured the timestamp. The up-front probe queued the build in 1.97 s. A repeat open returned the same ID. The source was ready at 9.53 s from the first open, with no chunks visible in sampled building states. Preparing during the build was refused.

Preparation after publication took 1.18 s, and a repeat returned the same prepared view. Across 31 warm pages, p95 was 31 ms and the largest response was 6,939 bytes. The 401 export pages reconciled 10,001 rows and 1,000,000 satang, including the late-collection evidence. The report counted 2,001 customers and 1,200,100 satang in lifetime revenue.

Before the up-front probe, the same fixture twice timed out inside the synchronous open path. Another run reached ready but immediately exceeded the deployment write-rate limit when preparing transactions. The final run used the up-front probe and completed without a write retry. These timings are local measurements.
